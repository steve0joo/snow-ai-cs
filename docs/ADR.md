# Architecture Decision Records

## 철학
6시간 MVP·프로토타입. **작동하는 최소 구현**을 선택한다. 되돌릴 수 있는 실패는 재실행으로 해결하고, 되돌릴 수 없는 실패(비밀 유출·데이터 재배포)만 방어한다. 과한 추상화·설정화·복구 로직을 넣지 않는다.

---

### ADR-001: 분석 대상을 SNOW + B612 2개로 한정 (구글플레이)
**결정**: 5개 앱 중 SNOW(`com.campmobile.snow`)와 B612(`com.linecorp.b612.android`)만. 둘 다 SNOW Corporation의 구글플레이 앱.
**이유**: 6시간에 5개는 앱당 표본이 얇아진다. 당초 신규 앱 101cam을 후보로 했으나 2026-09 확인 결과 101cam은 iOS 전용이라 구글플레이(우리 스코프)에서 수집 불가 → 자매 앱 B612로 대체. SNOW는 AI 생성/결제 문의의 본류, B612는 글로벌 사용자 기반이 커서 앱 간 유형 분포 비교가 가능하다.
**트레이드오프**: 101cam의 "신규 앱 온보딩 응축·지연 피드백" 차별화 통찰을 잃음(USER_JOURNEY.md에 참고 사례로 보존). SNOW·B612는 성격이 유사해 앱 간 대비가 101cam만큼 극적이지 않다.

### ADR-002: 구글플레이·한국어만
**결정**: App Store와 다국어 제외.
**이유**: App Store 리뷰 RSS는 동작이 불안정. 한국어가 매출 61%이자 검수 가능한 언어.
**트레이드오프**: 해외 약 40% 시장의 유형 분포 미검증(한계에 명시).

### ADR-003: taxonomy = 2축 + 1플래그, 주+부 유형 강제
**결정**: 유형(What, 1~7/0) × 챗봇 대응 가능성(So what, A/B/C) + `product_issue` 플래그. 다중 태깅 대신 주 유형 1 + 부 유형 1.
**이유**: 한 축만으론 "그래서 뭐?"로 끝난다. 다중 태깅은 비율 합이 100%를 넘겨 리포트 해석이 불가능하다.
**트레이드오프**: 복합 문의의 정보 일부 손실(부 유형으로 완화).

### ADR-004: LLM 1차 태깅 + 수동 검수, 본인 API 키로 스크립트 호출
**결정**: Anthropic API로 배치 자동 태깅 후 무작위 ~50건 수동 검수·일치율 산출.
**이유**: 500건 수동 태깅은 비현실적. 재현 가능한 파이프라인 확보. "AI로 운영 리소스를 줄이되 그 한계까지 아는 것"이 이 직무의 핵심 시그널.
**트레이드오프**: API 키·소액 비용 필요. 경계 유형에서 불일치 발생 → 이는 오히려 "체계 자체의 문제" 진단 소재가 됨.

### ADR-005: 층화는 수집 시 별점별, 원본 분포를 별도 기록
**결정**: 1점 40% / 2~3점 40% / 4~5점 20%로 층화 추출. 원본 별점 분포도 함께 기록.
**이유**: 무작위는 5점 칭찬에 표본을 낭비하고, 1점만 뽑으면 "분노 분포"가 된다. 원본 분포가 있어야 가중치 복원·방법론 방어가 가능하다.
**트레이드오프**: 표본이 전체 모집단을 그대로 대표하지 않음(가중치로 보정 가능).

### ADR-006: Harness 규약 유지 + Python 번안
**결정**: phases/step·execute.py 실행 규약은 그대로 두고, 스택과 AC만 Python으로 바꾼다.
**이유**: 프레임워크의 step 분할·가드레일·컨텍스트 누적은 유용하다. 웹앱 전제(npm build/test)만 이 프로젝트에 부적합하다.
**트레이드오프**: AC가 npm 빌드/테스트가 아니라 `py_compile` + 스모크라 검증 강도가 약함(수동 확인으로 보완).

### ADR-007: MVP 견고성 최소화 (일부러 안 하는 것)
**결정**: 수집 체크포인트 재개·지수 백오프·정교한 PII 정규식·비용 상한 로직을 넣지 않는다.
**이유**: 500건·1회성. 죽으면 재실행이 더 싸다. 남기는 방어는 유출 방지(.gitignore)·`userName` 드롭·JSON 파싱 try/except뿐.
**트레이드오프**: 대규모/반복 실행엔 부적합(의도된 한계).
